# Production layout regression

`layout.lpe` was extracted on 2026-10-13 from the user-supplied production
sample `~/Downloads/layout.txt`. The input was a JSON object member fragment
(`"layout": "lpe:...",`), not a complete JSON document. Extraction wrapped the
member in an object after removing its trailing comma and decoded it with
`JSON.parse`. Only CRLF-to-LF normalization and a final newline were added.
The `lpe:` prefix, Cyrillic text, widget IDs, duplicate style keys, trailing
commas, and the name `activeGrossValueTabsTabs` are intentionally unchanged.
Tests use the checked-in fixture and never need the original Downloads file.

## Coverage

- Full 937-line expression: parsing plus three stable parse/deparse cycles for
  each combination of LF/CRLF input and compact/formatted output.
- Reviewed structural expectations in `layout-structure.json`: root, call
  counts, all 64 widget IDs in order, and all seven tab/active-selection pairs.
- Extracted `it.title`, `color`, and `backgroundColor` expressions from all
  seven tab groups. Independent expected values cover selected, unselected,
  string-versus-number ID coercion, and missing-selection-ID cases.
- Every evaluation fragment runs both as an AST and as deparsed LPE source,
  with a fresh context. No evaluation result is generated from a JS oracle.
- The shared runner compares complete JS/Rust ASTs and rendered text, in
  addition to each implementation's round-trip stability and value assertions.
  The same 130 cases run against native Rust and the WASI CLI in existing CI.

The whole layout is **not** a standalone core-LPE evaluation test. Rendering
functions (`vbox`, `hbox`, `wrap`, `svg`), widget/layout operators (`#`, `@`),
`mapIt`, and `<-` need the production application's context. Its positional
`hash(key, value, ...)` calls also differ from core LPE's `hash` convention.
No substitute UI implementations or event-handler semantics are invented here.
Those constructs are covered by parsing/deparsing, not by rendering or clicking.

## Maintenance

`../production-layout.cases.json` is generated by
`../../scripts/production-layout-fixtures.mjs`. The generator extracts inputs
from the full layout, checks each tab's title and handler shape, and supplies
independently authored evaluation expectations. Do not hand-edit the generated
file. The structural snapshot should only change after reviewing the source.

From the repository root:

```sh
npm run build
node rust-impl/scripts/production-layout-fixtures.mjs
node rust-impl/scripts/production-layout-fixtures.mjs --check
node --test rust-impl/scripts/test-production-layout.mjs
cargo test --locked --manifest-path rust-impl/Cargo.toml --test production-layout
cargo build --locked --manifest-path rust-impl/Cargo.toml --bin lpe
node rust-impl/scripts/parity.mjs --filter production-layout
```

`npm run test:all` includes the JS production tests, Rust tests, generated-file
freshness check, and native parity. `npm run test:wasm` independently checks
fixture freshness and the JS production tests before including all shared
production cases in its JS/WASI comparison. Both commands run in GitHub CI.
See `../../README.md` for toolchain requirements. These are interpreter
regressions, not a production UI test.
